## Goal

Add a secret-scanning gate to the GitHub Actions CI workflow so the build **fails** when a credential is committed. Scanning covers the current tree (not git history), per the saved decision.

## Decisions (locked with the user)

1. **The Firebase Web API key is allowlisted as public config.** A Firebase Web config is public by design — it ships inside the browser bundle and cannot be kept secret. What protects the data is the Realtime Database rules plus API-key restrictions configured in the Google Cloud console. The allowlist is scoped to that one exact key so every *other* secret still fails the build.
2. **Scan the current tree only.** A secret that was committed and later deleted is out of scope for this gate. This is what makes the job pass on its first run: the tree currently contains no historical secret.

## Background

The committed tree already contains one credential-shaped value:

| Location | Value | Status |
|---|---|---|
| `.env:13` | `REACT_APP_FIREBASE_API_KEY=AIzaSyCi8kZHcinIYYLGTFKeFl_7skwAx4TiZDE` | Firebase Web API key — public by design |
| `README.md:116` | same key, in the env var table | documentation |
| `README.md:366` | `AIzaSy...` | truncated placeholder |
| `docs/security-report.md:114` | `AIzaSyB5cHT6x62tTe-g27vBDIqWcwQWBSj3uiY` | an **older, dead** key, quoted as the *before* baseline of the audit finding |

Gitleaks' default rule set flags `AIza…` as a Google API key, so both the live key and the historical one would trip a naive scan. The second is inert — it is quoted in prose to document what the audit found and the project it belonged to no longer accepts it — but it still matches the pattern and must be allowlisted too, or the job fails.

## Changes

### 1. New file: `.gitleaks.toml`

An explicit config, rather than relying on the tool's implicit defaults, so the allowlist is visible and reviewable in the repository:

```toml
title = "Secret scanning for the Burger Builder repository"

[extend]
useDefault = true

[allowlist]
description = """
Public, non-secret values that are intentionally committed.

A Firebase Web configuration is public by design: it is inlined into the
browser bundle at build time and cannot be kept secret. Access is constrained
by the Realtime Database rules in firebase.database.rules.json and by API-key
restrictions in the Google Cloud console (HTTP referrers + required APIs).

The second entry is an old, revoked API key quoted verbatim in
docs/security-report.md as the "before" baseline of the audit finding that
moved the key out of source. It is inert but still matches the pattern.
"""
paths = [
  '''(^\.env$)''',
  '''(^\.env\.example$)''',
  '''(^docs/security-report\.md$)''',
]
regexes = [
  '''AIzaSyCi8kZHcinIYYLGTFKeFl_7skwAx4TiZDE''',
  '''AIzaSyB5cHT6x62tTe-g27vBDIqWcwQWBSj3uiY''',
]
```

Each entry is deliberately narrow — exact paths and exact key values — so an unrelated secret in any of those files is still reported.

### 2. `.github/workflows/ci.yml` — new `secrets` job

Added as a **blocking** job (no `continue-on-error`), independent of the other jobs so a secret is caught even when the rest of the pipeline is red:

```yaml
  secrets:
    name: Secret scan
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          # The scan covers the current tree, so the shallow clone is enough.
          fetch-depth: 1

      - name: Scan for secrets
        uses: gitleaks/gitleaks-action@v2
        env:
          GITLEAKS_ENABLE_UPLOAD_ARTIFACT: 'false'
          GITLEAKS_NOTIFY_USER_LIST: ''
        with:
          # Fail the build on any finding.
          args: detect --no-banner --redact --verbose --source . --config .gitleaks.toml
```

Notes on the configuration:
- `args: detect …` scans the working tree. `--source .` is explicit so the scan is unambiguous.
- `--redact` masks the matched value in the log, so a real secret is never echoed into the build output.
- `GITLEAKS_ENABLE_UPLOAD_ARTIFACT: 'false'` disables the action's default SARIF upload, which requires the `security-events: write` permission. This keeps the job inside the workflow's existing `permissions: contents: read` block and avoids a permissions prompt on fork PRs.
- `GITLEAKS_NOTIFY_USER_LIST: ''` disables the action's default PR-comment notification, which would otherwise post the findings back into the pull request.

### 3. `README.md` — document the gate

Add a row to the CI/CD job table and a short paragraph explaining the allowlist and its rationale, so a future contributor who adds a real secret understands why the build failed and where the exceptions live.

## Verification

The gate must be proven both ways — that it passes on the clean tree and that it actually fails when a secret is introduced.

1. **YAML parses** — the workflow is loaded with a YAML parser and the job list is confirmed to include `secrets`.
2. **Clean tree passes** — run the scanner against the current tree; expect exit 0 and no findings.
3. **Injected secret fails** — write a file containing a syntactically valid secret that is *not* allowlisted (a fake AWS key and a fake private key), re-run the scanner, and confirm it exits non-zero and reports both findings. Remove the file afterwards.
4. **Existing gates unaffected** — `npm run lint`, `npm run test:coverage`, `npm run build`, `npm audit --audit-level=high` all still pass.
5. **Allowlist is narrow** — confirm the scanner still reports a secret placed inside `.env` or `docs/security-report.md`, since those paths are allowlisted only for the two specific Firebase key values, not for arbitrary content.

## Risks

| Risk | Mitigation |
|---|---|
| The allowlist is too broad and hides a real secret in `.env` | The allowlist is by **exact value**, not by path alone — the path entries only exclude the files from *path-based* checks; the regexes pin the two known public keys. A different secret in `.env` is still reported (verified in step 5). |
| Gitleaks' default rules change between versions and flag something new | The action is pinned to the `v2` major tag, and the config sets `useDefault = true` so new upstream rules apply automatically. A new finding fails the build loudly rather than silently passing. |
| The `AIza` allowlist masks a genuinely leaked Google API key elsewhere | Only the two known values are exempt. Any other `AIza…` key fails the build. |
| The scanner action cannot reach GitHub's API in a restricted network | The job needs no secrets and no `security-events` permission; artifact upload and PR commenting are both disabled. |
